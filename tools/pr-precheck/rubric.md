# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Plan fidelity | Plan context's scope, exclusions, test plan and Deviations beside every changed file and substantive hunk in the candidate diff. | The diff implements the bounded plan, or the plan's deviation notes explain each material addition, omission, or changed approach and why; the PR description acknowledges the resulting scope and any shortfall. Neither doing more nor doing less is silently presented as exact completion. | required |
| Observable behavior | Issue reproduction and plan test cases beside the candidate test-evidence commands, inputs, before/after observations, expected results, and controls. | Evidence exercises the actual changed behavior and shows an observable after result against the reproduced before and expected outcome. Distinct planned failure modes and affected controls are checked, or a bounded omission is explicitly disclosed and the completion claim narrowed to the demonstrated behavior. A generic suite pass, an expected result without an observed result, or a plan to test cannot substitute for the core repro. Judge coverage against the issue's repro and the plan's test plan: when the plan applies one identical change shape at sibling sites and its test plan names a representative trigger, observing that trigger satisfies this row without a separate test per site. Secondary controls (neighboring cases the plan expects to stay unchanged) need no raw output: a compact statement that they are unchanged, beside a directly observed core repro and a passing relevant suite, satisfies them unless contradicted. A distinct planned failure mode or trigger is not a control and needs its own observed result; beyond the core repro, a regression test in the diff that asserts that mode's expected outcome, inside a reported passing suite run, provides it. | required |
| Repository checks | Repo-facts check requirements and plan test plan beside actual command outcomes in test evidence and the PR testing section. | The applicable repository checks have been run with identifiable outcomes, or a specific unavailable check has its reason and resulting verification limit disclosed. Real failing or no-tests outcomes are reported as such; local results are not represented as hosted CI. No checks at all, a checklist alone, or an unexplained omitted gate fails. That applies to gates the repository or plan names as something to run (test suite, build, lint, type check, pre-commit); a template checklist item that names no command and attests a property visible in the diff, such as code formatted or text internationalised, is satisfied by the author's uncontradicted statement. | required |
| Description matches evidence | Candidate title, description and checklist claims beside the actual diff, commit list, plan/deviations and test-evidence results. | Claims of changed behavior, coverage, execution, success and completeness are supported by those artifacts and do not contradict them. Planned, completed and unverified work are distinguished; tests in a diff are not claimed as executed without outcomes. Honest limitations are preserved rather than replaced with broader claims. Fail a material claim (what changed, what was tested or run, what is complete) that the artifacts contradict or leave unsupported; a summary phrase the diff substantially bears out, a condensed output excerpt, or a concern about code the package does not show is a note, not a contradiction. | required |
| Focused reviewable diff | Every changed hunk and the commit list beside the issue and plan's bounded purpose. | The fix and its supporting tests/docs can be reviewed without unrelated edits, drive-by refactors, formatting churn, debug leftovers, dead or commented-out code. Necessary support is allowed; recording an unrelated cleanup as a deviation does not make it part of the fix. Do not use a file-count or line-count limit. | required |
| Repository standards | Repo-facts template asks, contribution/AI policy and material maintainer requests beside the PR's actual sections, issue reference, branch/commit metadata where supplied, and disclosure. Live mode also reads the course submission requirements. | Every applicable stated ask is addressed with real content or a justified N/A, including the issue link and required truthful AI-use disclosure. Respect the policy's actual scope and timing, not unstated conventions; absent AI policy in an eval package adds no disclosure requirement. In live coursework, AI assistance is always disclosed in Notes for Reviewers, all PR-template sections are filled, and CI may remain unchecked before opening as the assignment requires. | required |

## Verdict rule

Return accept only when every required check passes.
Any required fail or unclear returns reject; preferred checks, if added, never gate the verdict.
Use fail for a concrete contradiction or clearly missing required substance; use unclear when available evidence genuinely cannot decide.
An honestly disclosed shortfall does not automatically fail: apply each row to the bounded result actually claimed.
Disclosure cannot rescue invented output, a missing core reproduction, ignored mandatory template/disclosure asks, or unrelated changes.
The live pre-opening verdict is not a claim of green hosted CI or maintainer approval; report those separate requirements without ticking their boxes.
